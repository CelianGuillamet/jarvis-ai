# Versioned HTTP contracts

`contracts/v1.ts` is the canonical definition of the chat, status and Inbox response shapes and command replay states. Zod derives TypeScript types from the same schemas that validate runtime data. The dependency is pinned in both applications; it avoids maintaining a separate handwritten validator that can disagree with its type declarations.

Run `node scripts/sync-contracts.mjs` after changing the canonical source. Generated copies are committed under `api/src/contracts` and `web/src/core/contracts`. Each application's typecheck verifies byte-for-byte agreement with the canonical source, including in required CI. This preserves independent application installs and the existing Nest output layout without introducing a workspace build dependency.

Controller interceptors validate the serialized JSON shape (including Date serialization), return only schema fields and advertise `X-Jarvis-Contract: 1`. Invalid outgoing structures fail with 502/INVALID_RESPONSE and a sanitized message. The browser validates each endpoint before passing data to stores. A valid JSON document is insufficient if required fields or nested states are invalid. Existing browser types re-export schema-inferred types.

This boundary does not prove that an external mutation failed when its response cannot be validated. It must never trigger an automatic retry. Journal replay and Inbox operation identifiers retain their existing behavior.

Request DTO names now alias schema-inferred types; parameter pipes validate the shared strict request schemas. Unknown properties, invalid query arrays, null optional values and invalid conditional fields are rejected before service execution. The browser validates requests before transport and uses the same request limits. JAR-025 remains unfinished: validation of other provider responses and explicit partial/unknown outcomes still need completion. The schemas describe the current wire surface; this milestone is not a claim that every business outcome is already discriminated.

HTTP errors carry a stable `code` and a human-readable `message`. The global Nest filter distinguishes VALIDATION, UNAUTHENTICATED, FORBIDDEN, NOT_FOUND, CONFLICT, REQUEST_TOO_LARGE, UNSUPPORTED_MEDIA_TYPE, RATE_LIMITED, UNAVAILABLE, INVALID_RESPONSE and INTERNAL_ERROR. Body-parser and pre-authentication size/media/quota guards emit the same codes. Internal 5xx details are not returned to the browser. The client exposes `HttpError.code`, using the shared HTTP-status mapping when an external authentication handler returns its own error envelope. These transport categories do not assert whether a command had side effects; durable command outcomes remain a separate responsibility.

Model adapters validate their envelopes before returning text. Ollama requires `done: true` and nonempty message content; an explicit non-stop completion reason is rejected. OpenAI chat completions require a stopped completion and valid text content; Responses requires completed status and validated output text/message parts. Empty, truncated or malformed JSON responses raise INVALID_RESPONSE. Validation errors do not trigger model fallback requests. Endpoint incompatibility fallback remains available for the existing 400/404/415/422 cases. Tests stub transport; no live or paid model calls were made.

Malformed structured model decisions are not displayed as natural-language answers, even in simulation. Invalid ask choices and empty final responses are rejected. Legitimate non-structured conversational prose remains supported. Actionable malformed decisions may use the existing single repair attempt before failing; no tool execution occurs from an invalid decision.

Protocol references: [Ollama API](https://github.com/ollama/ollama/blob/main/docs/api.md), [OpenAI Responses types](https://github.com/openai/openai-node/blob/main/src/resources/responses/responses.ts).

Google Calendar read responses now validate calendar identifiers and event identifiers, start/end dates and optional field types before mapping. Malformed entries fail the read with INVALID_RESPONSE; missing identifiers no longer generate random event identities, and missing dates no longer silently drop events or fabricate a one-hour duration. Valid empty lists remain valid. Provider mutation receipts, Gmail validation and status degradation are still pending work.

Gmail list, metadata and full-message reads validate identifiers, provider timestamps, labels, headers and nested MIME parts before use. Invalid lists fail before metadata requests. Missing message dates no longer become the current time, and missing IDs no longer become the requested ID. Optional text content and legitimate empty lists remain supported. Tests use mocked Gmail transport. Send receipt handling remains separate because an invalid receipt cannot establish that sending failed.

Calendar creation/update and Gmail send receipts require a nonempty provider identifier at runtime. Gmail also validates the optional thread identifier. Malformed receipts raise INVALID_RESPONSE without retrying the mutation. This is not proof of failure: shared execution retains its existing unknown-state handling, and Inbox send recovery retains its uncertain send state. Calendar/Gmail deletion endpoints with empty successful responses do not require a JSON receipt. Explicit wire-level business outcomes remain pending.

Gmail label changes, trash and untrash also validate their returned receipt against the exact requested message identifier. Missing, malformed or wrong-target receipts fail without an adapter retry. Durable recovery remains responsible for deciding which follow-up actions can safely resume.

Status now includes required `availability.gmail` and `availability.calendar` fields with available, disconnected, permission_required, unavailable and invalid_response states. Failed optional reads retain null metrics rather than becoming zero. The dashboard displays the observed resource state separately from Google account connection. Successful local calendar reads remain available when Google is disconnected. Provider reads run concurrently; error details are not exposed. This describes read availability, not mutation outcomes.

Inbox apply results now require an explicit outcome: completed, simulated, partial or unknown. A saved send receipt with unfinished label/local steps is partial; an unconfirmed send is unknown. The dashboard store reports these separately and does not describe simulation as a real mutation. Catch-all per-message exceptions conservatively report unknown because the adapter cannot prove that no effect occurred. Existing ok/steps fields remain compatible, and retry identity behavior is unchanged. Generic command journal outcome classification is still pending.
